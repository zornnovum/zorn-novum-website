“I’m Out of Tokens”: Making AI Usage Go Further at Your Startup

By Keith Zorn, Founder of Zorn NovumNovember 12, 2026

“I’m out of tokens” is a familiar interruption for people building with AI. Development stalls, revisions hit a limit, or another task requires more credits.

For startups, better model selection, clearer prompts, and local AI can stretch available usage while keeping work moving. The opportunity is to match the work to the resources it actually needs.

Choose the model—and effort—for the task

Summarizing notes and reformatting text rarely require the same resources as debugging a difficult system or evaluating architecture.

Use lighter models for straightforward tasks, a capable general-purpose model for everyday work, and more demanding models when complexity justifies them. Apply the same judgment to reasoning settings. Additional effort can consume more usage without improving a simple answer.

Escalate when results fall short. Judge cost by the completed task, including retries and corrections.

Also identify the constraint: message allowances, API budgets, rate limits, and context limits require different responses. Local work can reduce cloud requests, but it does not replenish your account’s allowance.

Check the prompt before blaming the model

How you phrase a request can substantially change the outcome. An unclear objective, conflicting instructions, or missing context can turn a capable model into an expensive revision loop.

“Fix this code” leaves much more room for interpretation than a request identifying the failure, expected behavior, relevant files, and acceptance criteria.

Before retrying, consider whether the model misunderstood the deliverable, lacked necessary context, or followed an assumption you never intended. Correct that issue directly instead of repeating the same request.

Make clear whether you want analysis, a proposed change, or implementation. Provide an example when wording alone leaves room for ambiguity. Increasing model power cannot reliably compensate for contradictory requirements.

Give routine work a local home

A local model can handle drafting, summaries, feedback classification, documentation, and programming tasks without consuming cloud allowances.

Tools such as LM Studio, Ollama, and GPT4All offer accessible ways to run downloaded models. Some also offer cloud services, so verify where the selected model runs.

Start with existing hardware and a compatible quantized model. A 16 GB machine can be a reasonable place to experiment with a small 3–4B model; larger models depend heavily on available memory, graphics hardware, and context length. Check the application’s system requirements.

Free local inference still uses electricity, storage, hardware capacity, and staff time. Establish its usefulness before buying dedicated equipment.

Let local models program while you step away

Local programming work can include implementing a bounded feature, writing tests, refactoring a module, or investigating a reproducible bug. A compatible coding agent gives the model access to the files and tools needed to perform that work.

If immediate results are unnecessary, slower local processing can be a reasonable tradeoff. Assign a clear task before a meeting or break, then review the changes and test results afterward.

Set a reasonable limit on local debugging. When progress stalls, pass a concise summary of the problem and attempted fixes to a more capable cloud model. Review and test the resulting changes before merging or releasing them.

Combine local preparation with focused cloud work

Use local models to organize material, produce initial versions, and handle suitable implementation work. Bring a reviewed draft or focused technical problem to a cloud assistant when additional capability is worthwhile.

Preserve decisions in a short project brief. Request targeted revisions, supply relevant context, and settle requirements before repeatedly regenerating large deliverables.

Keep data handling explicit: local processing can keep supported work on your machine, while cloud escalation sends the selected material elsewhere. Review what crosses that boundary. Local processing details

Start with one local tool, one model, and a few recurring tasks. Measure usable output, elapsed time, correction effort, and cloud usage avoided.

The goal is more completed work from the resources available. A clear prompt, an appropriate model, and a defined escalation point can make the next usage limit much less disruptive.
